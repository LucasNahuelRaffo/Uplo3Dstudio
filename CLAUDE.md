# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page homepage for **Uplo3D Studio** (impresión 3D — sets de puntas, tapas de rueda, piezas a medida), exported from **Claude Design** (Anthropic's design tool) in its `x-dc` runtime format. There is no build system, no `package.json`, and no test suite — this is a static export meant to be dropped onto a host as-is.

## Files

- `Uplo3D Studio.dc.html` — the entire page. Root markup lives inside a custom `<x-dc>` element; a companion `<script data-dc-script>` holds the page's JS (handlers referenced from markup via `onClick="{{ handlerName }}"` bindings, e.g. `goHero`, `heroNext`, `sendForm`, `setEn`/`setEs`).
- `support.js` — the `x-dc` runtime (React-based renderer that parses the `<x-dc>` template + script and mounts it). **Do not hand-edit this file.** Its header states it is `GENERATED from dc-runtime/src/*.ts — do not edit. Rebuild with 'cd dc-runtime && bun run build'` — the `dc-runtime` TS source isn't part of this repo, so this file is a build artifact from elsewhere; treat it as vendored/opaque.
- `assets/logos/`, `assets/brands/` — brand logos used in the "Marcas que confían" marquee section.
- `uploads/` — page images and 3D models (`.glb`) rendered via `<model-viewer>` (Google's web component, loaded from unpkg in the HTML `<head>`).
- `.thumbnail` — preview thumbnail for the design, not page content.
- `index.html` — a copy of `Uplo3D Studio.dc.html` used as the GitHub Pages entry point. **Keep it in sync** (`cp "Uplo3D Studio.dc.html" index.html`) after every edit to the source file — GitHub Pages serves `index.html`, not the `.dc.html` file.

## Page structure (in `Uplo3D Studio.dc.html`)

Sections are marked with `data-screen-label` and appear in this order: Hero → Marcas (brand marquee) → Teaser Nosotros (`#about`) → Preview Servicios (`#services`) → Preview Proyectos (`#projects`) → Galería → Contacto + Footer (`#contact`).

- Styling is inline (`style="..."` on every element) — there is no external stylesheet besides the Google Fonts (Archivo, Inter, Space Mono) linked in `<helmet>`.
- Scroll-reveal / entrance animations are driven by `data-reveal` attributes and CSS transitions defined in the inline `<style>` block inside `<helmet>` (e.g. `@keyframes uploMarquee`, `uploFloat`, `uploSpin`), respected by a `prefers-reduced-motion` override.
- The header nav uses `onClick="{{ handlerName }}"` bindings resolved by the script inside `<script data-dc-script>` (not by `support.js` itself — `support.js` only provides the parsing/mounting runtime).
- 3D models (`mate.glb`, `set-puntas.glb`, `set-puntas-animado.glb`, `tapa-rueda.glb`) are shown via `<model-viewer>` tags pointing at files in `uploads/`.
- **GSAP + ScrollTrigger** are loaded via CDN (`jsdelivr`) in `<head>`, before `support.js`. Title elements get a scroll-driven "float up by character" reveal: mark any title text with `class="uplo-splitchars"` and it's picked up automatically by `window.__uploInitScrollFloat()` (defined at the top of the `<script data-dc-script>` block, called from `componentDidMount`). Because the `x-dc`/React runtime can re-render text (e.g. on language toggle via `setEs`/`setEn`), a `MutationObserver` re-splits and re-animates any `.uplo-splitchars` element whenever its text content changes — don't remove that observer when touching this logic, or language switches will silently break the animation.
- **The hero is light-themed** (`#FFFFFF` section, `#F7F7F7` inner panel) while Nosotros and Contacto stay dark. Two consequences to respect when editing it:
  - **There are two generated logo variants, and the original works on neither background.** `LOGO fondo transparente.png` (the master) mixes dark grey `#3F3F3E` in "uplo" with *pure white* in "studio", so half the wordmark drops out whichever way you go: on light backgrounds "studio" vanishes, on dark ones "uplo" does — which is what made the footer logo look cut in half. The old `filter:drop-shadow(0 0 1px rgba(255,255,255,0.4))` was a failed patch for this and has been removed everywhere. No CSS filter can fix it: `invert()` would wreck the yellow "3D". So: **`LOGO fondo claro.png`** (near-neutral light pixels → `#3F3F3E`) for light backgrounds — the hero and the mobile `.sm-bar`; **`LOGO fondo oscuro.png`** (near-neutral dark pixels → white) for dark ones — the fixed header and the footer. Both preserve alpha (clean antialiased edges) and skip chromatic pixels so the yellow survives. **Pick the variant by the background you're placing it on**; the master is only the source for regenerating them.
  - `.uplo-chip` and `.uplo-social` are **hero-only**, so their base rules carry the light colors directly. `.pill-nav-items` and `.uplo-lang` are **shared with the dark fixed header and the dark mobile panel**, so their light treatment is scoped as `#hero .pill-nav-items` / `#hero .uplo-lang` — never lighten those base rules. The nav pills take their color from the `--pill-text` custom property, which is why the scoped rule redefines that variable rather than touching `.pill`.
- `uploads/favicon.png` is generated too, and is **not** the wordmark: at 4.4:1 the full logo becomes an unreadable 7px-tall smudge in a 32px tab icon. It isolates the yellow "3D" (1.1:1) *by colour* — a plain crop of that region would drag in slices of the neighbouring "o" and "s" — and sets it on the brand dark as a rounded app-icon tile.
- The site's light-section text scale is: strong `#0E0E0E`, dimmed headline `#9A9A9A`, body/labels `#5A5A5A`. Note `#5A5A5A` and `#9A9A9A` **swap roles** between the dark and light schemes — on dark, `#5A5A5A` is the fainter of the two; on light it's `#9A9A9A`.
- **`.u-wave-bg`** is the repeating-radial-gradient wave texture, shared between the dark Contacto/Footer section (inline, dark greys) and the light sections — Hero, Marcas, Servicios, Proyectos, Galería (the shared class, light greys, one `<div class="u-wave-bg">` per section, always the first child of its container). It's `position:absolute;inset:0`, no `z-index`. **Do not give it a negative `z-index`** — that was tried and silently broke it: `position:relative` alone (without an explicit `z-index`) does **not** establish a stacking context, so a negative-z child escapes to whatever ancestor *does* establish one and can end up painting behind a completely unrelated part of the page. The correct (and only) requirement is that the **content sibling** painted after the wave also has `position:relative` — among positioned siblings with the same (auto) stack level, later-in-DOM wins, so the wave (first child) reliably stays behind the content (second child) regardless of which ancestor actually owns the real stacking context. Every section that uses `.u-wave-bg` needs its content wrapper positioned this way — see the four light sections' `data-reveal="0"` wrapper divs and the hero's `.u-hero-topbar`/`.u-hero-grid`.
- **Don't put `data-reveal` on a `<section>` that also has `.u-wave-bg`.** The scroll-reveal script sets `opacity:0→1` on whatever carries `data-reveal`; `opacity < 1` *does* create a stacking context (unlike bare `position:relative`), so while the section was mid-fade the wave was briefly, incidentally contained correctly — then the moment it reached `opacity:1` the stacking context vanished and the wave escaped, reading as "loads then disappears." Fix: keep `data-reveal="0"` on an inner content wrapper, not the section itself, so the section's background (and the wave) stay unconditionally visible and only the content fades in on scroll.
- **Responsive.** The single width breakpoint is **900px**. Below it, a StaggeredMenu-style hamburger (`.sm-bar` / `.sm-prelayer` / `#sm-panel`) replaces both desktop pill navs; at/above it the pill navs are shown and `body{zoom:0.9}` applies. Keep those two cutoffs identical — `zoom` scales the containing block that `position:fixed` resolves against in Chromium, so a mismatch makes the fixed bar render offset. Because all layout is inline styles, **every declaration in the `@media (max-width:899px)` / `(max-width:640px)` blocks needs `!important`** to beat inline specificity; elements are targeted via `u-*` classes added to the template purely as style hooks.
- **The mobile menu's open state is a `data-menu-open` attribute on `document.body`, deliberately outside the React tree.** All of its visuals are CSS transitions keyed off `body[data-menu-open="1"]`, and the base (attribute-absent) rules double as both the closed state and the close animation, so closing needs no JS reset. This is what makes it immune to the runtime's re-renders — the panel is re-rendered on every language toggle and every 5.2s hero autoplay tick, and since no element inside the tree carries menu state (no ref, no toggled class, no inline transform), those re-renders are no-ops. `window.__uploInitMenu()` only writes that attribute and syncs ARIA; its listeners are delegated on `document` and singleton-guarded via `window.__uploMenuBound` so a remount can't double-bind. Do not move this state into `Component.state`.
- Nav items expose a **`goMenu`** handler alongside `go` (`renderVals()`): it closes the menu *before* scrolling, because React's delegated `onClick` fires ahead of the document listener and `goTo()` would otherwise scroll while `body` still has `overflow:hidden`, losing the scroll.
- A few values are **computed geometry in JS** and can't be fixed from CSS (`mvStyle`, `vidCards`, `projShift` in `renderVals()`). They read a `narrow` state field fed by a `matchMedia('(max-width:899px)')` listener. Note `projShift` assumes a **260px card step** on mobile (240px card + 20px gap) — if you change `.u-proj-card`'s mobile width, update `projShift` to match or the carousel desyncs.
- The header and hero navs use a **PillNav**-style component (React Bits), adapted to CSS-only interactions (`.pill-nav-items`/`.pill-list`/`.pill`/`.hover-circle`/`.label-stack` classes in the `<style>` block) instead of the original's GSAP timelines/React refs, since this runtime can re-render the nav on every `activeNav`/language state change — CSS `:hover`/`.is-active` avoids re-binding refs after each render. `navItems` in `renderVals()` only supplies `label`, `go`, and `activeClass` now.

## Working in this repo

- To preview the page, just open `Uplo3D Studio.dc.html` in a browser (or serve the folder with any static file server) — `support.js` boots the runtime and renders the `<x-dc>` template client-side.
- Edits to copy, layout, or styling happen directly in the inline HTML/CSS inside `Uplo3D Studio.dc.html`; there's no source-of-truth elsewhere to sync from.
- Image/model assets referenced by the page live under `uploads/` and `assets/` with relative paths — keep new assets there and reference them the same way.
